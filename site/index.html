Draft ERC-8473 · the policy side of ERC-7943

uRWA Policy

An ERC-7943 token asks one external contract, its policy, whether each movement of its balances may happen. The policy answers with a bytes32: TRANSFER_OK permits, and anything else rejects with a reason. The same policy answers the token's ERC-7943 checks, so a wallet's pre-flight runs the same checks as the transfer it predicts.

Why a separate policy

ERC-7943 standardises what a permissioned token exposes: account checks (canSend, canReceive), a transfer pre-flight (canTransfer), frozen balances and forcedTransfer. It deliberately leaves open how the token reaches its decisions.

Those decisions, about identity, jurisdiction, lock-ups, holder caps and settlement hours, change more often than a token's accounting, and different teams write and audit them. So tokens keep them in a separate contract, and each implementation invents its own interface to it. A compliance provider has to integrate with every token family separately, and a token cannot switch providers without a custom adapter.

ERC-8473 standardises that boundary. A token and a policy written by different teams work together, and when both follow it, the guarantees ERC-7943 asks of a token's checks hold.

What it defines

  • Movements. For every movement of its balances, the token builds a TransferContext labelled with the authority under which the movement happens: TRANSFER, EXECUTED, FORCED, MINT or BURN.
  • Decisions. The token asks the policy before any balance changes. One fixed non-zero value permits. Every other value, zero included, rejects.
  • Pre-flights. The same policy answers canSend, canReceive and canTransfer, and canTransfer runs the same checks as the movement it predicts.
  • State. A policy that keeps state, such as a holder count, is told about each completed movement through an authenticated callback, and is called on every installation so it can set that state up.

Status

  • The ERC is a draft, submitted to ethereum/ERCs in pull request 2128. It can still change.
  • It is discussed on Ethereum Magicians.
  • The reference implementation in fepvenancio/urwa-policy has a token (ExampleToken), the same token with an executor channel (ExampleExecutorToken) and a policy (ExamplePolicy). It shows the specification working, and it is not audited.
