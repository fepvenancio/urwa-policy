Implementing

Writing a token or a policy

What a token and a policy have to get right to follow the specification, with the reason for each rule. Most items are requirements. Those marked should are recommendations, and those marked advice come from the Security Considerations. The reference contracts are one way to meet all of them. These checklists are a reading aid: the requirements themselves are in the specification, and they win wherever the two differ.

A token

A token implements one of the ERC-7943 interfaces and IERC8473, which adds policy(), the PolicyChanged event and the ERC8473PolicyRejected error. The reference token is ExampleToken, an ERC-20 built on OpenZeppelin Contracts 5.

Send every movement through the policy.

Mints, burns, transfers and forced transfers all ask it first. The reference routes them through one internal function, _move, so no path can skip it. On OpenZeppelin, _update is the override that catches every balance change.

Pick the kind by authority, and the first match wins.

Label an escrow return that a request directed as TRANSFER. Keep FORCED for enforcement paths, and never use EXECUTED or FORCED for the base standard's transfer functions.

Ask before anything changes, and call nothing else in between.

For TRANSFER, MINT and BURN, the operation must not change balances, ownership, total supply or frozen amounts before checkTransfer, except through earlier movements of the same operation. Between the check and the balance change, make no external call except to the policy, so nobody can change what the check saw.

Read the policy address once per movement.

Use it for checkTransfer, wantsAfterTransfer and afterTransfer, so a replacement halfway through cannot split approval and notification across two policies.

Treat every failure as a rejection.

STATICCALL the checks. A revert, no code, fewer than 32 bytes, or any value but TRANSFER_OK rejects. wantsAfterTransfer must be exactly 0 or 1. With no policy installed, reject everything. Revert with ERC8473PolicyRejected(reason) when the policy rejects should.

Keep your views working during a movement.

Balances, ownership, total supply and frozen amounts must not revert while a movement or onInstall runs, because the policy reads them then.

Notify after the event, before the recipient.

After the transfer event, call wantsAfterTransfer and, if it returns true, afterTransfer with the identical context. Do both before any ERC-721 or ERC-1155 receiver hook, and guard so no movement can start inside afterTransfer.

Build the pre-flight from the same code.

Same kind, same token checks, and the same context with operator = from. Build data as the movement builds it: empty, or only values the token derives from its own state, never anything the caller supplied. Never revert, and copy at most one word of the policy's answer should. The reference calls the policy at a low level in _permits to manage that. When both from and to are zero, return false.

Combine your own account conditions with the policy's.

If the token adds account-level conditions of its own, such as a frozen wallet, canSend and canReceive return true only when both the policy and those conditions permit, and movements apply them to from and to in the same way.

Let the zero address pass the account checks.

canSend(address(0)) and canReceive(address(0)) return true without calling the policy. The account checks of a mint pre-flight then fall on the receiver alone and those of a burn on the sender alone, and canTransfer still performs both checks, as ERC-7943 requires.

Keep your own checks free of the caller.

For TRANSFER, MINT and BURN, the pause, the frozen amount and any account conditions of your own may not read msg.sender, operator, tx.origin or the remaining gas, or the pre-flight would answer differently from the movement.

On a forced move, unfreeze at least the frozen part that moves.

If frozen tokens move, first reduce the frozen amount by at least that part, and emit Frozen before Transfer. The reference reduces it by exactly that part.

If you offer EXECUTED, the token verifies and restricts.

Verify the holder's signature in the token, and restrict the function to accounts you granted the capability, independently of the instruction. Otherwise the movement is a TRANSFER. The instruction may also name which of them carries it out. The ERC leaves the instruction's design to you advice: record each one as used so it cannot be repeated, sign every value the movement takes from it, enforce a deadline in the token, and offer a cancel to holders without code.

Tell an EXECUTED pre-flight who executes.

Take the executing account as an argument and build the context exactly as its execution would, including operator and data. Never answer yes when your own checks or the policy would reject.

Guard the installation.

Check ERC-165 support for 0x9cb56a99 and emit PolicyChanged. Call onInstall once policy() returns the new policy, and revert if it reverts. No movement or other installation may begin while it runs. Never let the outgoing policy stop an installation. Never install from the constructor, or from an initializer a proxy's constructor runs: install from an initializer called after the proxy is deployed.

Advertise your own interfaces.

Return true for supportsInterface(0x0505c8c9), the IERC8473 identifier, and for the identifier of the ERC-7943 interface you implement, such as 0x3edbb4c4 for the fungible one.

Process batches item by item.

Check, move, emit and notify each item before the next, so caps stay exact. If any item is rejected, the whole batch reverts. An ERC-1155 token on OpenZeppelin overrides _update to apply one item at a time.

In the specification: Token requirements. The reference's _update, _move and _permits are quoted in Reference Implementation, and the full source is ExampleToken.sol and ExampleExecutorToken.sol.

A policy

A policy implements IERC8473Policy: three checks (checkSend, checkReceive, checkTransfer), the callback pair (wantsAfterTransfer, afterTransfer), onInstall, and ERC-165. Most of the rules below keep the pre-flight honest and stop a stranger from touching state.

Decide by returning, never by reverting.

The checks are views. Return TRANSFER_OK or a reason. A revert reads as a failure, not a decision.

Use the common reason names. should

When you reject for one of the seven listed reasons, return keccak256 of its name, so wallets can explain it. Name any other reason yourself, and document what you return.

Depend only on arguments, storage and the block.

A check may use its arguments, persistent storage, and the block's timestamp, number and chain identifier. Never msg.sender, tx.origin or the remaining gas, so anyone simulating gets the token's answer. This is narrower than ERC-7943 allows, on purpose.

Keep the account checks about accounts.

checkSend and checkReceive may not hold balance checks or amount limits. Those belong in checkTransfer.

Never permit what the account checks reject.

For every kind but FORCED, checkTransfer must fail when checkSend(from) fails for a non-zero from, or checkReceive(to) for a non-zero to. That lets one check per movement cover ERC-7943's three. For FORCED, still check the receiver unless the token documents a bypass should.

Ignore operator for the predicted kinds.

TRANSFER, MINT and BURN decisions may not depend on who submits, or on state the operation changed before the check, such as a vault's assets during a deposit. For EXECUTED, avoid state the operation changes, such as the record that an instruction was used, because a pre-flight cannot reproduce it.

Read the kind on every path that can permit.

In Solidity, an out-of-range enum in a calldata struct reverts only when it is read. A path that permits without reading kind could permit a kind that does not exist.

Never turn a failed call into a permission.

If a call to a rule or a registry reverts or runs out of gas, reject. Otherwise a caller could pick a gas limit that silences one rule.

Treat a check call as proof of nothing.

Anyone can call the checks with any context. A permitting answer authorises nothing, and does not mean the caller is the token or that a movement happened.

Accept callbacks only from the token.

afterTransfer and onInstall revert unless msg.sender is the token named. A call from one token must not change state that governs another, unless the policy authenticates every token it serves.

Set movement-derived state again on every onInstall, or revert.

No "already initialised" guard: a reinstall must not keep the old state. A policy without such state may do nothing else. Prefer state you can verify on-chain, such as a holder list checked against totalSupply(), over a number someone hands you advice.

Be honest in wantsAfterTransfer, and keep rejections in checkTransfer.

Return true whenever you rely on the callback. canTransfer never runs the callback, so a rule enforced in afterTransfer would break the pre-flight. Bound your gas should: a check that runs out of gas rejects the movement.

Read data only for a token whose encoding you know. advice

Nothing in the context names the encoding, and abi.decode ignores extra words, so a policy shared by tokens with different encodings can read one value as another without reverting. Fix the encoding per token.

Advertise the interface.

Return true for supportsInterface(0x9cb56a99), or no token will install you. Implement ERC-165 in full: a token that checks through OpenZeppelin's ERC165Checker, as the reference does, also needs true for 0x01ffc9a7 and false for 0xffffffff.

The example policy's rules

The cap

A move to someone who already holds is never capped. A zero amount and a transfer to yourself never count. A move that takes the sender's whole balance to a new holder leaves the count unchanged, so it passes while the count is at or below the cap. Any other new holder needs the count below the cap. Lowering the cap below the count admits no new holder until enough leave, while existing holders keep trading and can exit.

The count

afterTransfer accepts calls only from the token, for that token. It ignores zero amounts and self-transfers. When the sender's balance reaches zero it subtracts one. When the receiver's balance after the move equals the amount just received, the receiver is new or was refilled, and it adds one. A forced transfer is counted like any other move, even though the cap did not apply to it.

Mistakes to avoid

The specification's Security Considerations go through these in detail. The short version:

  • Mislabelled kinds. A token that labels a holder-directed movement FORCED skips every rule that exempts enforcement. The policy cannot tell, so the kind has to be right in the token.
  • Trusting the caller of a check. Checks are public views. Never grant anything, or record anything, because a check was called.
  • Treating a pre-flight as a promise. It is a snapshot of the state at the time of the call. The state can change before the transaction lands.
  • Unbounded gas. A check that loops over a growing list will one day run out of gas and reject every movement.
  • Sharing a policy across tokens with different data encodings. One token's value is read as another's, without a revert.
  • Assuming which policy is installed. Read policy(), and watch PolicyChanged, before relying on a policy's rules.

Testing

The repository's tests are Solidity tests run by Hardhat 3, with forge-std's cheatcodes. Fuzz tests check that each pre-flight equals the outcome of the movement it predicts, over eligibility, pause, frozen amounts, caps and amounts. For canTransfer the comparison stays within the balance, because ERC-7943 leaves a shortfall to the base standard.

To run them:

git config --global url."https://github.com/".insteadOf "ssh://git@github.com/"
npm ci --ignore-scripts
npm test
npm run test:isolated

The first line is needed only without a GitHub SSH key: the lockfile records forge-std as a git+ssh dependency. test:isolated runs the same tests with a fresh EVM per call. The suites deploy the reference contracts in their setUp, so testing your own token or policy against them means changing what setUp deploys and adjusting the tests that pin the reference's own roles and errors.
