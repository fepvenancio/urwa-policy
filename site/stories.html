User stories

Six movements, call by call

Each story follows one person's goal through the reference contracts: who calls what, in which order, what the policy is told, and what happens when the answer is no. The contracts are ExampleToken, ExampleExecutorToken and ExamplePolicy. The policy here combines an allowlist with a holder cap. Story 5 also uses a settlement window, which ExamplePolicy does not have: the tests show it with a second policy, ExecutedRulesPolicy.

1. A transfer 2. A wallet's pre-flight 3. A mint and a burn 4. A forced transfer 5. An executed instruction 6. Replacing the policy

Reading the diagrams: a solid arrow is a call, a dashed arrow is what comes back, a rounded box is a step inside the contract, and the shaded bar on the token is the reentrancy guard. Numbers match the steps under each diagram.

Story 1 · TRANSFER

A holder sends tokens to another verified investor

As a holder, I want to send 100 tokens to another investor on the allowlist, so that a trade we agreed settles on-chain.

  1. The holder calls transfer(to, 100). OpenZeppelin's ERC-20 routes every balance change to _update, which the token overrides. It picks the kind and calls _move, which does the rest under a reentrancy guard.
  2. No forced transfer is pending and both addresses are non-zero, so the kind is TRANSFER.
  3. The token's own checks run. If the token is paused it reverts with EnforcedPause. If part of the balance is frozen and 100 is more than the unfrozen part, it reverts with ERC7943InsufficientUnfrozenBalance, or with ERC20InsufficientBalance when 100 is more than the whole balance.
  4. It builds the context and reads the policy address once. It uses that address for every call in this movement, so a policy replaced halfway cannot split the approval and the notification.
  5. It calls checkTransfer(ctx) as a STATICCALL. Anything other than TRANSFER_OK reverts with ERC8473PolicyRejected(reason). A revert, a policy with no code, or an answer shorter than 32 bytes reverts too.
  6. The balances change and the ERC-20 Transfer event is emitted. Nothing external happens between step 5 and this one.
  7. It asks wantsAfterTransfer(). The answer must be exactly 0 or 1.
  8. The answer is true, so it calls afterTransfer with the identical context. The policy updates its holder count: minus one if the sender's balance is now zero, plus one if the receiver is new.
  9. The guard is released and transfer returns true.

What the policy sees

from, tothe holder, the receiver
amount, tokenId100, and 0 for ERC-20
operatorthe holder, or the spender for transferFrom
kind, dataTRANSFER, empty

When the answer is no

  • The receiver is not on the allowlist: RECEIVER_NOT_ELIGIBLE.
  • The holder is no longer on it: SENDER_NOT_ELIGIBLE.
  • The receiver would be a new holder and the cap is full: MAX_HOLDERS.
  • The token is paused, or the tokens are frozen: the token's own error, before the policy is asked.

Story 2 · pre-flight

A wallet checks a transfer before sending it, and explains a no

As a wallet developer, I want to know before my user signs whether a transfer will go through, and why not, so that they never pay gas for a transaction that fails.

  1. The wallet calls canTransfer(from, to, 100) as a read-only call. It never reverts.
  2. The token picks the kind as the transfer would, and runs its own checks. If the token is paused or the amount is frozen, it answers false here without asking the policy.
  3. It builds the same context the transfer would build, except that operator is from, and calls checkTransfer in a way that cannot revert.
  4. The policy rejects, so canTransfer returns false. A bool carries no reason.
  5. To find out why, the wallet simulates the transfer itself with eth_call, sent from the holder's address. Nothing is broadcast.
  6. The token runs the real movement path, which asks the policy again.
  7. The simulation reverts with ERC8473PolicyRejected(reason), and the wallet decodes the reason from the revert data. A pause or frozen tokens would come back as the token's own error, such as EnforcedPause or ERC7943InsufficientUnfrozenBalance, instead.
  8. The wallet compares the reason with keccak256 of the common names and shows a message. A reason it does not recognise is still a no: it shows a generic message, and never treats the value as permission.

Messages a wallet might show

ReasonMessage (an example)
SENDER_NOT_ELIGIBLEYour account can't send this token right now.

Good to know

  • The simulation is a wallet technique, not something the ERC requires. The ERC gives the error and the common names, which is what makes the technique work across tokens.
  • Any account may call a policy's checks with any context, so a wallet can also read policy() and call checkTransfer directly. That returns the policy's reason, but skips the token's own checks.
  • An answer is a snapshot. The state can change between the check and the transaction, so the transaction can still fail.
  • canTransfer leaves a plain balance shortfall, allowances and roles to the base standard, so check those as for any ERC-20.

Story 3 · MINT and BURN

An issuer mints to a new investor, and an investor redeems by burning

As an issuer, I want to issue 500 tokens to an investor who just passed onboarding, so that the subscription settles, and I want the holder cap to count them. As an investor, I want to burn my tokens when I redeem.

  1. The issuer calls mint(to, 500). Only an account with MINTER_ROLE may. That role check is access control, which stays outside the policy.
  2. from is the zero address, so the kind is MINT.
  3. The token's own checks run. A pause stops a mint. There is no sender, so no frozen amount applies.
  4. The context has from = 0 and operator = the issuer. The policy may not use operator for a mint.
  5. The policy checks that the receiver is on the allowlist, and that a new holder fits under the cap. A receiver who already holds tokens is never capped.
  6. The balance changes and Transfer(address(0), to, 500) is emitted.
  7. The token asks wantsAfterTransfer(). The example policy keeps a count, so it answers true.
  8. In afterTransfer, the receiver's balance now equals the amount just received, so the policy counts a new holder.
  9. The mint returns.

The burn

The investor calls burn(amount) on their own tokens. to is zero, so the kind is BURN. The pause and the frozen amount apply, the policy checks that the investor may send, and the cap never blocks a burn. If the investor burns everything, afterTransfer removes them from the count.

The pre-flights

canTransfer(address(0), to, 500) predicts the mint, with operator = 0. canTransfer(investor, address(0), amount) predicts the burn. Neither looks at the mint role.

Story 4 · FORCED

A court order moves tokens from a holder

As the token's enforcer, I want to move 100 tokens out of a holder's account under a court order, even though the token is paused, part of the balance is frozen and the holder cap is full, so that the order is carried out.

Only an account with ENFORCER_ROLE may call forcedTransfer(from, to, 100). The token unfreezes only what the move needs, and only when frozen tokens move: if the unfrozen part covers the amount, nothing is unfrozen and no Frozen event is emitted. With 1,000 held and 950 frozen, moving 100 leaves 900 frozen. A freeze above the balance keeps withholding: with 1,500 frozen, moving 100 leaves 1,400. The specification requires Frozen before Transfer. The reference emits ForcedTransfer last, after the policy's callback.

The token marks the next movement as forced with a flag in transient storage, and _update clears it before anything else. So a forced transfer cannot lend its kind to an ordinary transfer later in the same transaction. The test suite checks this with a helper contract that does both in one call while the token is paused, and the second one reverts with EnforcedPause.

What the policy sees

from, tothe holder, the receiver the order names
operatorthe enforcer
kind, dataFORCED, empty in the reference

A token may pass a reference to the legal order in data for FORCED, as long as it documents the encoding.

When the answer is no

  • The receiver is not eligible: RECEIVER_NOT_ELIGIBLE. Enforcement skips the token's own checks, not the policy's check on the receiver.
  • The sender is not checked, and the cap does not apply. The new holder is still counted.
  • canTransfer does not predict a forced transfer, because a policy may decide it by who the enforcer is (OPERATOR_NOT_ALLOWED).

Story 5 · EXECUTED

A transfer agent settles a holder-signed instruction

As a transfer agent, I want to carry out a transfer the holder signed off-chain, inside the settlement window the policy allows, so that the trade settles without the holder sending a transaction.

The instruction

ExampleExecutorToken extends ExampleToken with a settlement channel. The holder signs an EIP-712 Instruction(from, to, amount, instructionRef, deadline, executor), in a domain that names the token and the chain. The signature covers every field, so the executor can change none of them. A holder that is a contract signs through ERC-1271.

Only an account with EXECUTOR_ROLE can call executeInstruction. That restriction, which does not depend on the instruction, is what makes the movement EXECUTED and not TRANSFER. The executor field narrows it further: a non-zero value names the one account that may carry it out, and zero means any account with the role.

The policy sees operator = the executor and data = abi.encode(bytes32 instructionRef, uint256 deadline). The token enforces the deadline itself; the policy only reads it.

One use, any order

A reference can be used once per holder, in any order. With a sequential nonce, one expired instruction would hold up every later one from that holder until something used up its nonce. When the policy rejects, the whole call reverts, including the record that the reference was used, so the instruction can be tried again until its deadline. An instruction refused while the window was closed can still settle when it opens.

When the answer is no

  • The window is closed: the policy's reason, WINDOW_CLOSED in ExecutedRulesPolicy.
  • A registry the policy relies on did not answer: CHECK_UNAVAILABLE. Nothing was recorded, so the executor can try again before the deadline.
  • Expired, already used, the wrong executor or a bad signature: the executor token's own errors for the instruction, before the policy is asked.
  • The pre-flight is canExecute(instruction, signature, executor). It takes the executor as an argument and builds the context the execution would.

The holder changes their mind

Because a refused instruction stays valid until its deadline, the holder needs a way to stop it. Any holder can call cancelInstruction(instructionRef), which writes the same record a settlement writes. It is not a movement: it needs no role, does not ask the policy, and works while the token is paused.

Story 6 · installation

An issuer replaces the policy

As the token's admin, I want to move the token to a new compliance provider's policy without redeploying the token, so that holders keep their balances and the new rules apply from the next movement.

Only an account with DEFAULT_ADMIN_ROLE may call setPolicy(policy, data) on the reference token. Who may install is outside the ERC. In step 2 the token uses OpenZeppelin's ERC165Checker, which makes three calls: 0x01ffc9a7 must answer true, 0xffffffff false, and then 0x9cb56a99 true. The token passes data to onInstall unchanged, and the policy decides what it means.

ExamplePolicy takes a list of addresses in strictly ascending order. It adds up their balances and counts the non-zero ones. If the sum equals totalSupply(), nobody outside the list holds tokens, so the count is exact at that moment, however old the list is. Accounts that hold nothing may be listed, so the list can name everyone who might hold by the time a timelocked installation runs.

When the answer is no

  • The new policy does not support the interface: ExampleToken_PolicyNotSupported.
  • Someone outside the list holds tokens: ExamplePolicy_HoldersIncomplete(sum, supply).
  • The list repeats an address or is out of order: ExamplePolicy_HoldersNotAscending(index).
  • Anyone but the token calls onInstall: ExamplePolicy_OnlyToken.

In every case the installation reverts and the previous policy stays.

Good to know

  • A token cannot install a policy from its constructor. Until the constructor returns, the token has no code, so onInstall could not read it. That is safe, because a token with no policy rejects every movement.
  • Every list entry costs a balance read, so the list has a size limit. For larger holder sets, the specification's Security Considerations describe a staged path: an interim policy that keeps new holders out while it counts over several transactions.
