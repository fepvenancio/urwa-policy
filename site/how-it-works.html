How it works

One question, asked the same way every time

An ERC-8473 token never decides its compliance rules itself. Before any balance changes, it describes the movement to its policy and asks for a decision. This page explains the pieces that conversation is made of, in the order you meet them.

The two contracts

The token keeps the balances and the checks that belong to the token itself: a pause if it has one, the frozen amounts ERC-7943 defines, and any account-level conditions it adds, such as a frozen wallet. The policy holds the other rules: who may hold the token, how many holders it may have, lock-ups, settlement hours. The token never decides those. It asks.

Three paths cross the boundary between them. Movements (transfers, mints, burns, forced transfers, and executed instructions) all go through one internal function. The ERC-7943 checks that wallets and protocols call go through a second path that never reverts. Replacing the policy goes through a third.

The decision value

Every check returns a bytes32. Exactly one value permits: TRANSFER_OK, which is keccak256("TRANSFER_OK"), or 0xf059ed42…5c77fd3f. Every other value rejects, zero included.

Zero is what Solidity returns from a function whose return value is never assigned, for example in a branch the author forgot. If zero permitted, that bug would let every movement through. Here it rejects them. A function selector would be a worse success value: a contract that echoes its calldata answers checkTransfer with exactly bytes32(checkTransfer.selector), because the first argument word of a call with one dynamic tuple is the offset 0x20. The reference's test suite proves both with a forgetful policy and an echoing contract.

A policy decides by returning a value, never by reverting. A pre-flight cannot tell a revert that means "no" from a bug or an out-of-gas, so the token treats every revert as a failure, and a failure rejects.

Reason codes

A rejection carries a reason, so operators and wallets can tell why a movement failed. A policy should make each reason the keccak256 of an upper-case name, and document the reasons it returns. The token should revert with ERC8473PolicyRejected(reason), and the reference does.

Seven common reasons have names that every policy should use when it rejects for that reason, so a wallet can explain them without knowing which policy it is talking to. Any other reason gets a name of the policy's own. A value the wallet does not recognise is still a rejection: integrators must never treat it as permission.

NameThe policy rejects because
SENDER_NOT_ELIGIBLEfrom, or the account checkSend is asked about, may not send, for example because it is not verified or is in an excluded jurisdiction
RECEIVER_NOT_ELIGIBLEto, or the account checkReceive is asked about, may not receive, for the same kinds of reason
LOCKED_UPthe tokens that would move are still in a lock-up or holding period
MAX_HOLDERSthe movement would take the number of holders above a cap
WINDOW_CLOSEDthe movement falls outside the hours or dates the policy allows
KIND_NOT_ALLOWEDthe policy does not allow this kind of movement, such as a TRANSFER when holders may move tokens only through an executor
OPERATOR_NOT_ALLOWEDthe movement is EXECUTED or FORCED, and the policy does not accept operator as the account carrying it out

The token's own checks never reach the policy, so they are not policy reasons. In the reference, a pause reverts with EnforcedPause and frozen tokens with ERC7943InsufficientUnfrozenBalance. The reference policy returns SENDER_NOT_ELIGIBLE, RECEIVER_NOT_ELIGIBLE and MAX_HOLDERS from the list, and UNKNOWN_TOKEN, a name of its own, when it is asked about a token it does not serve.

Kinds: whose authority moves the tokens

Every movement carries one of five kinds, and policies treat them differently. A lock-up binds the holder but not a court order. A holder cap binds ordinary transfers and issuance, but not enforcement. The kind is decided by facts the token can check on-chain, not by the name of the function or the business process. The token gives each movement the first kind whose condition holds, in this order.

OperationKind
transfer, or transferFrom by a spenderTRANSFER
A holder's signature that any account, or the payee, may submit, as in ERC-3009TRANSFER
Returning escrowed shares to the account a request names, when the request is rejected or cancelledTRANSFER
An issuer's mint; an ERC-4626 share mint on depositMINT
A holder's burn; an ERC-4626 share burn on redeem; an executor carrying out a signed burnBURN
An authorised executor carrying out a holder-signed transfer instructionEXECUTED
ERC-7943 forcedTransfer, for any reason, including a lost-key recovery the holder asked for off-chainFORCED
Minting a fulfilled claim to a recovery account instead of the claimantFORCED (from zero)
Burning without the holder's on-chain direction, or despite failed account checks or frozen tokensFORCED (to zero)

The order records a real defect in the code this ERC was extracted from. An asynchronous vault returned the escrowed shares of a rejected redemption to the request's controller and labelled the movement FORCED. Enforcement was exempt from the holder cap and the pause, so that path delivered shares past both. The request directed the movement, so it is a TRANSFER.

Because FORCED comes first, a forced movement can have a zero from or a zero to, but never both. The base standard's transfer functions, such as transfer and transferFrom, never produce EXECUTED or FORCED. The set of kinds is closed: a policy must reject any value outside it, and adding a kind means a new interface.

The transfer context

The token describes each movement to the policy in one struct, TransferContext. These eight fields are everything the token tells the policy about the movement. A rule may also read the token's balances, total supply and frozen amounts, the policy's own storage, other contracts' state that no operation of the token changes, such as an identity registry, and the block's timestamp, number and chain ID.

FieldWhat it holds
tokenThe token whose balance changes. When the token calls its policy, this is the token itself, so one policy can tell the tokens it serves apart.
fromThe account the tokens leave. Zero for a MINT, and for a FORCED movement that creates tokens.
toThe account the tokens reach. Zero for a BURN, and for a FORCED movement that destroys them.
tokenIdZero for an ERC-20 token. For other tokens, the identifier of the token moved.
amountThe quantity moved, and 1 for an ERC-721 token.
operatorThe account that called the token: msg.sender, or the sender a trusted ERC-2771 forwarder resolves, never tx.origin. For EXECUTED it is the executor, and for FORCED the enforcer.
kindOne of the five kinds above.
dataEmpty for TRANSFER, MINT and BURN, or only values the token derives from its own state, never anything the caller supplied. For EXECUTED and FORCED the token may pass more, such as an instruction reference and deadline, and must document the encoding.

For TRANSFER, MINT and BURN, the policy's decision may not depend on operator. That is what lets a pre-flight, which has no real caller, give the answer the movement would get.

Pre-flights give the movement's answer

A wallet or a protocol asks canTransfer(from, to, amount) before it tries a transfer. The answer is only useful if it matches what the transfer would get, so a token runs the same checks with the same context. Two things differ: operator is from instead of the caller, and the policy is called in a way that never reverts, given enough gas.

So at the same state, and given enough gas, canTransfer gives the decision that a transfer, a transferFrom by a spender, a mint (zero from) or a holder's burn (zero to) would get. The reference's test suite fuzzes all four. Some things stay outside it:

  • A plain balance shortfall, and allowances, which ERC-7943 leaves to the base standard. With nothing frozen, canTransfer can say true for more than the balance, and the transfer still fails with ERC20InsufficientBalance.
  • Access control, such as a mint role, which this ERC leaves out of the token's checks.
  • The policy's callback, which a pre-flight does not run, so a failing callback only shows in the movement.

canSend and canReceive return true only when the policy's checkSend or checkReceive permits and the token's own account-level conditions do too. The zero address is the exception: it passes both without a call. The zero address is the source of every mint and the sink of every burn, so the account checks of a mint fall on the receiver alone and those of a burn on the sender alone.

FORCED and EXECUTED movements are not predicted by canTransfer, because their decisions may depend on who carries them out. A token that offers an executor can give it a pre-flight of its own that takes the executor as an argument. The reference's is canExecute(instruction, signature, executor).

Solidity's try/catch is not enough for a pre-flight that must never revert, because it does not catch a failure to decode bad return data. The reference makes the call by hand in _permits, which the specification quotes in full.

The after-transfer callback

A policy that keeps state, such as a holder count, needs to know when a movement completed. After the balances change and the transfer event is emitted, the token asks the same policy wantsAfterTransfer(). If it answers true, the token calls afterTransfer with the identical context it passed to checkTransfer. If the callback reverts, the movement reverts.

  • Authenticated. afterTransfer reverts unless the caller is the token named in the context, so nobody can feed the policy fake movements.
  • Strict answers. wantsAfterTransfer must return exactly 0 or 1. Any other word, or a short answer, reverts the movement, so a malformed reply cannot skip the callback.
  • No new movements. The token guards its movement path, so afterTransfer cannot start another movement. It may read the token's balances, which are already the new ones.
  • Before the recipient. The callback completes before any ERC-721 or ERC-1155 receiver hook runs.
  • Records, does not enforce. afterTransfer must not reject a TRANSFER, MINT or BURN. A rule that can reject belongs in checkTransfer, because canTransfer never runs the callback.

Installing a policy

A token with no policy rejects every movement. On every installation (the first one, a policy coming back, and the policy that is already installed), the token checks that the new policy supports the interface, 0x9cb56a99, through ERC-165, and emits PolicyChanged. Once policy() returns the new policy, it calls onInstall(token, previousPolicy, data) on it. The reference emits the event, then switches, then calls. If onInstall reverts, the installation reverts and the old policy stays.

A policy cannot tell on its own that it was swapped out and back. While another policy was installed it saw no movements, so any count it kept went stale. That is why onInstall must set every piece of state the policy derives from movements again, or revert. The outgoing policy is never asked, so a broken or hostile policy cannot block its own replacement. Story 6 shows the calls.

Each failure below ends in a rejection, never in a permission. The reference has a test for each row, most of them with a deliberately faulty policy.
